> 关联文档：`docs/ARCHITECTURE.md`；`docs/design-disk-health.md` 仅作参考，非依赖项

> 更新说明（0.22.33）：
> - 页脚四项按行业惯例排序：数据覆盖、生成时间、上一期报告、下一期预计。

> 更新说明（0.22.32）：
> - 页眉只保留报告周期，数据覆盖移到页脚。
> - 页脚删除报告周期栏，避免与页眉重复。

> 更新说明（0.22.31）：
> - 登录来源 IP 统计不识别或展示 IP 归属地，公网来源统一显示“公网”。
> - 页尾“上一期报告”展示上一期报告的具体生成时间，生成时从历史报告归档读取，不写“已生成”。

> 更新说明（0.22.30）：
> - 磁盘明细“健康 / 结论”列移到设备之后、容量之前，保持状态列紧邻实体。
> - 登录来源 IP 统计“最后活动”补全年份；来源合计行同时汇总成功与失败次数，并保留 Fail2ban 封禁说明。

> 更新说明（0.22.29）：
> - 事件脉冲图曲线约束在横轴基线上方，不越出绘图区。
> - 磁盘明细“健康 / 结论”列只展示健康结论，不混入温度；温度由“物理硬盘健康状态”表负责。
> - 删除独立“安全事件”模块；登录来源 IP 统计整宽展示，失败来源合计与 Fail2ban 封禁结果并入该表。

> 更新说明（0.22.22）：
> - 第 2 章“安全与入侵研判”合并风险摘要与异常研判为单张明细表：研判项、风险等级、结论、说明；风险计数保留在章节引导句，避免同一事项重复展示。

> 更新说明（0.22.23）：
> - 磁盘容量使用率图、设备 I/O 对比图继续保留用于比较；原“磁盘容量 · 按物理硬盘”“磁盘 I/O 周期摘要”“容量预测（磁盘部分）”三张明细合并为一张“磁盘容量与 I/O 周期明细”。
> - “容量预测”只保留非磁盘资源（如内存），磁盘容量、增长和预计达到阈值时间统一放在磁盘明细表。

> 更新说明（0.22.24）：
> - 删除“容量预测”模块，磁盘明细不再单独展示容量预测表。
> - 磁盘明细删除“挂载点”列，挂载点只作为采集聚合依据，不再在报告中单列。

> 更新说明（0.22.25）：
> - 设备 I/O 对比图在每根条形右侧直接标注具体读/写量，不依赖表格才能读取数值。
> - 磁盘容量与 I/O 明细表“容量 / 已用”列改用具体容量值（GB/TB），不再用百分比表示已用。
> - 存储与数据安全按物理硬盘逐行展示 SMART、温度和状态，不按固定硬盘数量排版；RAID 与文件系统独立成区。

> 更新说明（0.22.26）：
> - “服务与应用状态”重新设计为指标卡 + 统一服务清单：名称、当前状态、类型、周期错误/重启、最近启动、说明；不再用项目小表和稳定性表重复展示。
> - 服务清单补充 cron 与 Docker 停止容器汇总，避免关键服务缺行。

> 更新说明（0.22.27）：
> - 删除“服务稳定性周期指标”图表，统一服务清单作为稳定性明细的唯一载体。
> - Docker、虚拟机、失败服务、关键服务四个概览指标固定单行四列展示，不在窄屏回退为两列。

> 更新说明（0.22.28）：
> - 全报告多列表格按行业通用报表惯例排序：实体/标识列（IP、设备、服务、用户、事项等）先行，状态/等级次之，核心指标居中，备注/时间靠后；时间线、更新执行记录等以时间列开头。不再使用“重要性”作为排序依据。

> 更新说明（0.22.21）：
> - 正式定稿事件脉冲图语义：Y 轴为事件影响等级（低/中/高），节点颜色表示事件影响等级，不与第 2 章风险评级计数直接对比。
> - 移动端宽表统一使用 `wide-table-wrap` 横向滚动，不通过折行压缩关键字段；覆盖服务稳定性、登录来源、用户统计、磁盘与网络明细表。
> - 登录来源 IP 统计必须展示每个来源的成功/失败次数；Top N 无法覆盖全部失败时，增加“其他失败来源”汇总行，使来源行合计与登录失败总数一致。
> - 计划重启、服务最近启动时间、VM 运行时长必须由同一重启时间线生成；摘要连续运行天数不得与周期内计划重启矛盾。
> - 安全更新按低风险处理时，必须说明判定依据，例如未发现已利用漏洞告警、已纳入下一维护窗口。

> 更新说明（0.22.20）：
> - 资源章节新增磁盘容量阈值图和设备 I/O 周期累计对比图，分别突出接近 90% 的容量风险，以及每块盘的累计读写量与峰值繁忙度。
> - 服务章节新增错误次数与重启次数对比图，帮助快速定位需要观察或已失败的服务。
> - 三张图均保留对应明细表；图表用于比较和定位，表格用于保留精确数值、时间和状态。

> 更新说明（0.22.19）：
> - 事件脉冲图统一使用单一内联 SVG 坐标系，曲线、节点、引线、标签和日期不再混用 HTML 绝对定位。
> - 事件标签改为语义色直接文字加短引线，不使用方框、背景底板或前置图标；标签只描述事件，不展示实时数值。
> - 事件节点改为实心语义色圆点：正常灰、信息蓝、关注琥珀、异常红；同日多事件使用上下独立标注位。
> - 窄屏保留时间线最小可读宽度，允许横向浏览，不压缩事件标签字号。

> 更新说明（0.22.18）：

## 1. 文档目的

本文档用于定义 DebNAS 新增「运维报告」模块的产品范围、用户价值、报告内容、功能需求与验收标准。

该模块面向无法每天查看服务器的用户，提供按周、按月、按半年、按年生成阶段性报告的能力，让用户用几分钟了解服务器在过去一段时间的整体状态，而不是登录系统逐项查看。

本文档是后续设计、开发、测试与迭代的唯一需求依据。

---

## 2. 产品背景

### 2.1 背景

DebNAS 用户通常是家庭或小型办公环境的 NAS 使用者。他们完成部署后，不会每天登录系统检查：

- CPU 是否长期过高。
- 内存是否接近耗尽。
- 磁盘是否正在快速增长。
- 网络流量是否异常。
- 是否有陌生登录或大量失败登录。
- 是否有服务静默挂掉。
- 是否有安全更新长期未安装。
- 磁盘、文件系统、RAID 是否出现健康风险。

这类问题在发生时往往不引人注意，但会在数周或数月后演变为服务不可用、数据丢失或安全事件。

### 2.2 产品定位

运维报告不是实时监控面板，而是服务器的「阶段性体检报告」。

它回答用户三个核心问题：

1. 服务器这段时间整体是否健康？
2. 有哪些已经发生或正在恶化的问题？
3. 接下来我该做什么？

---

## 3. 产品目标

### 3.1 产品目标

1. 让用户无需日常登录即可掌握服务器资源、存储、安全、服务和硬件状态。
2. 在问题变得严重前，通过周期报告提示用户采取行动。
3. 为磁盘扩容、内存升级、网络流量规划、服务维护等决策提供历史数据依据。
4. 通过登录与安全审计，帮助用户发现异常访问和潜在风险。
5. 保持 DebNAS 轻量、纯 Bash、可重复执行的产品理念，不引入重型监控平台。

### 3.2 成功标准

- 用户可以在 5 分钟内读完一份报告并了解服务器整体状态。
- 用户可以选择最近 7 天、30 天、180 天、365 天生成报告。
- 报告可在交互菜单、CLI、定时任务三种入口生成。
- 报告包含资源、存储、登录安全、服务状态、系统维护、硬件健康等核心内容。
- 定时报告固定为每周一次，年度报告自动发送，同时支持手动生成。
- 本地报告只保留 HTML；邮件内容优先 Markdown，不支持时降级为邮件支持的格式。
- 数据保留至少 13 个月，满足年度报告需求。
- 数据不足时，报告明确说明数据覆盖范围，不误导用户。
- 报告包含敏感登录信息时，文件和邮件权限受到保护。

## 4. 目标用户与使用场景

### 4.1 目标用户

| 用户 | 特点 | 报告诉求 |
|------|------|---------|
| 家庭 NAS 用户 | 部署后很少登录，关注文件、照片、影音服务 | 知道服务器是否正常、磁盘是否够用、有没有异常登录 |
| 小型办公 IT 管理员 | 同时管理一到多台服务器 | 用周报/月报掌握资源趋势、安全事件和扩容时机 |
| 技术爱好者 | 熟悉 Linux，喜欢查看细节 | 能获取原始数据和深度指标，但不希望被实时监控工具绑定 |

### 4.2 典型使用场景

1. **每周快速巡检**
   用户每周收到或主动生成一份 7 天报告，确认 CPU、内存、磁盘、登录、服务无异常。

2. **每月容量规划**
   用户查看 30 天报告中的磁盘增长趋势，判断是否需要在未来 1-3 个月内扩容。

3. **半年/年度复盘**
   用户生成 180 天或 365 天报告，回顾服务器稳定性、安全事件、升级记录和资源增长。

4. **异常后排查**
   用户发现服务不可用后，通过历史报告确认是否在报告周期内出现过 OOM、重启、磁盘错误或登录异常。

## 6. 报告范围审计

### 6.1 审计结论

用户最初提出的范围是：

- CPU 使用情况。
- 内存使用情况。
- 磁盘使用情况。
- 网络流量使用情况。
- 每个用户的登录次数和登录时间。

这些属于「资源使用」和「登录审计」两个板块，但不足以回答“服务器这一阶段是否健康”。一份合格的阶段性服务器报告，至少还应覆盖系统可用性、存储数据安全、安全事件、服务状态、软件更新和硬件健康。

### 6.2 建议纳入报告的板块

| 优先级 | 报告板块 | 为什么必须纳入 | 数据来源 |
|--------|---------|---------------|---------|
| P0 | 系统可用性 | 用户首先需要知道服务器是否稳定运行 | `/proc/uptime`、`last`/`wtmpdb`、`/proc/loadavg`、内核版本 |
| P0 | 重启与关机记录 | 非计划重启通常说明系统异常 | `last reboot`、`wtmpdb last -x`、journald |
| P0 | 磁盘容量与增长趋势 | NAS 最常见的故障是磁盘写满 | `df`、`sar -F`、自有容量快照 |
| P0 | 文件系统/RAID/磁盘健康 | 防止数据丢失，提前发现坏盘和降级 RAID | 由 `ops-report` 内置读取 `smartctl`、`/proc/mdstat`、`findmnt`、dmesg/journald，不依赖磁盘健康模块 |
| P0 | 关键服务状态 | 服务静默挂掉是最难被用户发现的问题 | `systemctl --failed`、`service-query` |
| P0 | 登录安全与失败登录 | 发现暴力破解、陌生登录和账号滥用 | `lastb`、`auth.log/journald`、`fail2ban`，并按来源 IP 汇总成功/失败次数 |
| P0 | 安全封禁情况 | 确认防火墙/Fail2ban 是否正在保护服务器 | `fail2ban-client status`、防火墙规则、threat-ips 状态 |
| P0 | 软件更新 | 安全更新长期未装是主要风险之一 | `apt`、`sys-patches` 检查结果 |
| P0 | 关键日志异常 | OOM、内核错误、服务崩溃应优先展示 | `journalctl`、`/var/log/kern.log`、`/var/log/syslog` |
| P0 | 资源占用大户 | 帮助用户知道“谁吃掉了 CPU/内存” | `atop`/`pidstat`、`sar` 周期采样 |
| P0（v1.0） | Docker 容器状态 | DebNAS 大量用户运行 Docker，容器重启和停止不能遗漏 | `docker ps`、`docker stats`、容器事件 |
| P0（v1.0） | 虚拟机状态 | DebNAS 支持 VM，虚拟化实例故障应纳入报告 | `virsh`、`systemctl`、进程状态 |
| P1 | 硬件温度/风扇/电源 | 高温是 NAS 长期稳定性的重要风险 | `sensors`、`smartctl`、`hddtemp` |
| P1 | 外网 IP 变化 | 动态 IP 变化会破坏远程访问和端口映射 | 网络状态、DDNS/Tailscale |
| P1 | SSL 证书到期 | 证书过期会导致 Web/远程访问直接不可用 | 本地证书扫描、openssl |
| P1 | 定时任务执行情况 | 计划任务静默失败会导致更新、同步、清理全部失效 | cron 日志、`systemctl list-timers`、DebNAS 状态 |
| P1 | 周期对比 | 只有“当前值”没有“变化”无法判断趋势 | 上期报告、历史状态文件 |
| P2 | 用户账户与权限变更 | 新增、删除、锁定账户可能反映安全隐患 | `/etc/passwd` 快照、`auth.log`、sudo 日志 |
| P2 | 安全配置漂移 | SSH、防火墙、Cron 配置被意外修改时应提示 | 配置快照、文件哈希 |
| P2 | 应用层错误 | Web、媒体服务等应用错误率升高应被看到 | journald、应用日志 |
| P2 | UPS 状态 | 断电和电池老化会影响数据安全 | NUT/apcupsd |
| P2 | 性能回归 | 本期平均负载较上期明显升高应提示 | 历史报告对比 |

### 6.3 不建议纳入

- 记录用户执行的每一条命令：数据量大、隐私风险高，且属于专业审计系统范畴。
- 每容器每秒级指标历史：需要自建采集和存储，v1 不划算。
- ISP 网络质量、公网延迟波动：不是 NAS 自身可准确测量的指标。
- 多主机聚合和告警平台：属于独立产品方向，不应塞进单机报告模块。

### 6.4 报告信息分级建议

为避免报告过于冗长，建议将内容分为三层：

| 层级 | 内容 | 面向用户 |
|------|------|---------|
| 本周概览 | 周结论、每日状态时间条、关注事项 | 只想快速确认是否安全 |
| 常规详情 | 资源趋势、登录汇总、服务状态 | 希望了解本周/本月情况 |
| 深度数据 | 逐日峰值、逐接口流量、最近登录明细 | 技术用户排查和复盘 |

### 6.5 磁盘健康实现途径

`disk-health` 模块目前仅为意向功能，尚未实现且不一定实现。`ops-report` 必须独立完成磁盘健康检查，不将其作为前置依赖。

内置实现方式：

- SMART：通过 `smartctl` 直接读取当前健康状态、温度、坏道计数和寿命。
- RAID：通过 `/proc/mdstat` 和 `mdadm --detail --scan` 检查阵列是否正常、降级或重建中。
- 文件系统：通过 `findmnt`、`dmesg`、journald 检查只读挂载、异常卸载和文件系统错误。
- `smartctl` 作为 `ops-report` 自身依赖处理，缺失时按项目依赖体系自动安装 `smartmontools`。
- 每次报告生成时保存关键磁盘健康快照到状态目录，用于后续周期对比；该文件属于状态数据，不属于配置文件。
- 若未来 `disk-health` 模块实现，可通过其结果文件复用，但不作为前置条件。

## 7. 报告内容设计

### 7.1 报告结构

报告采用单页长报告框架，按以下顺序组织：

```text
1. 本周概览（每日状态时间条 + 需要关注事项）
2. 安全与入侵研判（含风险摘要、异常研判）
3. 系统可用性与事件时间线
4. 资源使用情况
5. 存储与数据安全
6. 网络
7. 服务与应用状态
8. 登录与安全审计
9. 系统维护情况
10. 建议与行动项
```

### 7.1.1 图文并茂布局

报告不应只使用表格，应通过本周概览和图表帮助用户快速获取关键信息。

布局要求：

### 7.2 本周概览

- 周结论：一句话说明本周最重要结论。

- 不使用指标卡、指标清单或决策清单。
- 事件节点使用颜色和短标签表达，不解释内部判定规则。
- 不展示图例小字或开发提示；曲线含义由 Y 轴标签体现，节点含义由事件标签体现。
- 事件脉冲图不展示开发提示小字或解释性引导文案。

- 事件标签只使用简短事件描述，例如“磁盘 I/O 异常”；不展示百分比、时间戳或其他动态数值，具体数据由后续章节提供。

- 关注事项只给结论，详细原因由后续章节提供。
- 不重复第 2 章风险摘要。

### 7.2.1 本周概览版面设计

- 顶部：周结论 + 蓝色左侧强调线。
- 中部：事件脉冲图，X 轴为 7 天日期，Y 轴为事件影响等级三级刻度，曲线表达每日影响等级趋势，节点表达事件。

视觉要求：

- 事件节点使用灰/蓝/琥珀/红的实心圆点，与事件影响等级一致：正常灰、信息蓝、关注琥珀、异常红；不等同于第 2 章风险评级。

- 不使用图例小字；曲线含义由 Y 轴标签体现，节点含义由事件标签体现。

- 日期标签与图形保持紧凑间距并与每日节点列对齐。
- 不显示额外轴标题文字。
- 事件脉冲图不设置面积填充、背景框、阴影或发光；曲线使用强调蓝，网格线和垂直辅助线使用中性灰。

- 关注事项不使用卡片盒，使用细线分隔和编号。
- 周结论使用 `24px` 大标题，说明不超过两行。
- 每个正文章节标题下增加一句结论引导，避免章节只有表格堆叠。

总体状态建议由以下因素综合判定：

- CPU 是否长期超过 90%。
- 内存是否长期超过 90% 或发生 OOM。
- 磁盘使用率是否超过 85%，或预测 30 天内写满。
- 是否出现文件系统错误、SMART 告警、RAID 降级。
- 是否有服务进入 failed 状态。
- 是否有大量失败登录或陌生来源登录。
- 是否有安全更新长期未安装。
- 是否有内核错误、OOM、非计划重启。

### 7.2.2 红黄绿评级规则

评级由脚本内固定阈值计算，不提供用户自定义配置，阈值按行业通用经验定义。

| 状态 | 触发条件 |
|------|---------|
| 红色 | 任一磁盘使用率 ≥ 90%，或预测 30 天内写满 |
| 红色 | 文件系统错误、RAID 降级、SMART 告警 |
| 红色 | 发生 OOM、内核 panic、关键服务连续失败 |
| 红色 | CPU 或内存长期 ≥ 95% |
| 黄色 | 任一磁盘使用率 ≥ 80%，或预测 60 天内达到 90% |
| 黄色 | CPU 长期 ≥ 80%，或内存长期 ≥ 85% |
| 黄色 | 存在安全更新未安装 |
| 黄色 | 存在非关键服务 failed |
| 黄色 | 报告周期内失败登录异常集中 |
| 绿色 | 未触发红色和黄色条件 |

评级结果只用于报告提示，不替代具体告警通知；即使总体为绿色，仍展示详细数据供用户查看。

### 7.2.3 系统可用性与事件时间线

- 周期可用性百分比，例如 `7 天可用性 99.95%`。
- 计划内停机次数和计划外停机次数。
- 重启、关机、系统更新、服务重启、异常登录等统一按时间排列。
- 每个事件包含时间、事件、影响、状态。
- 非计划停机、内核错误、OOM 必须作为事件优先展示。
- 报告只展示停机分类结果：计划内、非计划、意外停电的次数和持续时间，不展示判定规则和命令。

停机分类规则：

| 类型 | 判定依据 |
|------|---------|
| 计划内停机 | 匹配维护窗口记录、`apt/dpkg` 更新历史、用户主动标记的计划维护 |
| 非计划重启/关机 | 无维护记录，但 `wtmp`/`journald` 存在重启或关机记录 |
| 意外停电 | `journald` 出现 Power-Off/Power loss、NUT 记录 ONBATT/LOWBATT、下一次启动无正常关机记录 |

实现要求：

- 报告模块维护一个状态文件，记录维护窗口、上次启动时间和 `boot_id`。
- 每次生成报告时比对 `journalctl --list-boots`、`last -x reboot/shutdown` 和 NUT/UPS 事件。
- 计划内维护必须在维护窗口内发生；更新后重启优先标记为计划内。
- 无法归类的事件默认标记为非计划，并在报告中说明判定依据。

### 7.3 资源使用情况

周期数据与瞬时数据边界：

- 周期聚合指标：CPU、内存、磁盘容量增长、磁盘 I/O、网络流量、登录次数、更新次数，必须使用报告周期内统计值。
- 当前状态指标：硬件温度等，只作为补充信息；Top 程序优先使用周期采样平均，无采样数据时不得作为周期结论。
- 无历史周期数据时，不展示瞬时值代替周期结论，应提示数据不足。

#### CPU

- 报告周期内平均使用率、最高使用率。
- 与上一周期对比：平均使用率和峰值变化。
- 趋势图使用本周期实线 + 上一周期虚线双线对比。
- 最繁忙日期和最繁忙时段。
- 系统负载均值变化。
- 单核/多核分布（可选）。
- 过去一周硬件平均利用率 Top 5 程序；基于周期采样，无采样数据时提示覆盖不足。

#### 内存

- 平均使用量、峰值使用量。
- 与上一周期对比：平均使用量和峰值变化。
- 趋势图使用本周期实线 + 上一周期虚线双线对比。
- 可用内存最低值。
- Swap 使用情况。
- 是否发生过 OOM 事件。
- 过去一周硬件平均利用率 Top 5 程序；基于周期采样，无采样数据时提示覆盖不足。

#### 磁盘

- 按物理硬盘统计：设备、健康/结论、容量/已用、增长量、预计写满时间；“健康/结论”紧邻设备列，“容量 / 已用”使用具体容量值（GB/TB），不使用百分比作为已用列。
- 同一块物理硬盘的多个挂载点合并统计，仅用于采集聚合，不在报告中单列。
- RAID/设备映射盘按实际物理盘或 RAID 阵列展示；无法识别时显示逻辑卷并注明。
- 与上一周期对比的增长量。
- 磁盘 I/O：基于 sysstat 周期采样的平均读/写吞吐、峰值繁忙度、最繁忙磁盘和时段。
- 不使用报告生成时刻的瞬时 I/O 值代替周期摘要。
- 周期读写量：基于 `/proc/diskstats` 差值或 `sar -d` 汇总，展示周期内累计读/写字节数。
- 磁盘容量图使用物理盘使用率的横向条形图，必须标注 90% 阈值；接近阈值的设备使用琥珀色，精确容量、增长和预计达到时间仍保留在明细表。
- 设备 I/O 图使用统一的 TB 轴比较每块物理盘的周期累计读/写量，并在每根条形右侧直接标注具体读/写量；峰值繁忙度标注在设备行右侧，平均读写速率、最繁忙时段和结论仍保留在明细表。
- 磁盘容量、I/O 合并为一张“磁盘容量与 I/O 周期明细”表，不再分拆为三张重复表；容量预测自 v2026.11.1 起以「磁盘容量预测」表单独展示（按近 N 天增速外推到 90% 告警线）。

#### 网络

- 流量单位统一：容量使用 B/KB/MB/GB/TB，速率使用 bps/Kbps/Mbps/Gbps。
- 阶段汇总：周期内总接收、总发送、总流量、日均接收/发送。
- 每个网卡接口的收发总量和日均流量。
- 平均/峰值速率。
- 最繁忙日期和时段。
- 网卡错误、丢包、冲突统计。
- 当前公网 IP 是否发生变化。
- 与上一周期对比：总流量、日均流量变化。
- 只统计物理网卡接口，不统计 `lo`、`docker*`、`veth*`、`br-*`、`virbr*`、`tun*`、`tap*`、`wg*`、`tailscale*` 等虚拟接口。
- 多物理网卡服务器逐个列出接口，并提供“物理网卡合计”。
- 物理网卡识别优先使用 `/sys/class/net/<接口>/device` 是否存在；存在 bond 时只统计 bond 聚合口，避免成员网卡重复计数。

### 7.4 存储与数据安全

- 文件系统使用率及增长预测。
- 文件系统错误、只读挂载、异常卸载。
- RAID 状态：正常、降级、重建中。
- 物理硬盘 SMART 按块逐行展示：设备、SMART 结果、温度、状态，不按固定硬盘数量排版；硬盘较多时继续复用 `wide-table-wrap`。
- 快照/子卷/存储池状态（如果系统存在）。

### 7.5 登录与安全审计

#### 登录汇总

- 报告周期内成功登录总次数。
- 与上一周期对比：成功登录、失败登录、封禁数量变化。
- 独立登录用户数。
- 每个用户成功/失败登录次数。
- 每个用户活跃天数：报告周期内有成功登录的天数。
- 每个用户活跃占比：该用户成功登录次数 / 周期内全部成功登录次数 × 100%。
- 每个用户的首次登录和最后登录时间。
- 每个用户使用过的来源 IP 数量。

#### 登录来源 IP 统计

- 每个来源 IP 的成功登录次数、失败登录次数和最后登录时间。
- 来源 IP 行合计必须与登录失败总数一致；Top N 无法覆盖全部来源时，增加“其他失败来源”汇总行并给出剩余次数。
- 来源合计行同时汇总成功与失败次数，Fail2ban 封禁数量直接展示在来源 IP 表内，不单设“安全事件”模块。
- 来源类型：本地、局域网、公网。
- 报告周期内公网 IP 是否发生变化。

#### 登录时段分析

- 24 小时成功登录时段分布柱状图。
- 每个用户最常登录的时间段。
- 非工作时间（如凌晨 00:00-05:00）成功登录标记。
- 用户出现与其历史习惯明显不同的时段登录时，标记为“时段异常登录”风险。
- 时段异常登录展示具体时间、用户、来源 IP，并在“时段异常登录”模块给出处理建议。

#### 登录明细

- 最近 N 条登录记录：时间、用户、服务、终端、来源 IP。
- 本地登录和远程登录分开展示。
- 标记 root 远程登录、非工作时间登录等高风险项。

#### 安全配置漂移

- SSH 配置、防火墙规则、计划任务、用户账户是否发生变化。
- 变化项展示变更时间、对象、影响。
- 无变化项统一显示“无变化”，避免用户逐一核对。

### 7.6 服务与应用状态

- `systemd` 失败服务列表。
- 最近停止/重启的重要服务。
- Docker 容器总数、运行中/已停止数量。
- 重启次数异常的容器。
- Docker 镜像、卷、端口映射变化（可选）。
- 虚拟机运行状态和最近启动时间。
- 监听端口变化（可选）。
- 服务稳定性周期指标：关键服务的周期错误次数、周期重启次数、最近启动时间和运行状态。
- 服务最近启动时间、VM 运行时长与“重启/关机”事件必须来自同一重启时间线；摘要中连续运行天数不得与周期内计划重启矛盾。
- 不使用服务瞬时 CPU/内存占用作为周期结论；如需占用数据，只展示周期采样平均值。
- 章节采用“指标卡 + 服务与应用清单”布局：指标卡展示 Docker、虚拟机、失败服务、关键服务概览；清单统一展示类型、名称、周期错误、周期重启、最近启动、当前状态和说明。
- 四个概览指标固定单行四列展示；服务清单必须包含 cron 等关键 systemd 服务，以及 Docker 停止容器汇总行。
- 不单独展示服务稳定性图，周期错误、周期重启、最近启动和状态统一由服务清单呈现。

### 7.7 系统维护情况

- 报告周期内执行更新的次数。
- 已安装更新包总数、安全更新数量、常规更新数量。
- 更新包明细：包名、旧版本、新版本、更新时间。
- 更新执行记录表：按执行时间列出每次更新的包名、版本变化和更新类型。
- 更新来源：`apt`、`dpkg`、`sys-patches`。
- 系统版本更新：操作系统版本、内核版本、关键组件版本、上一版本、更新时间。
- 当前内核版本与升级历史。
- 可用的安全更新数量和常规更新数量。
- 安全更新按低风险展示时，必须附带判定依据，例如未发现已利用漏洞告警、已纳入下一维护窗口。
- 最近一次系统更新检查时间。
- 最近一次成功安装更新的时间。
- 重启需求：是否存在待生效内核/驱动更新。
- Journal 错误摘要：按服务统计周期内错误日志数量。
- SSL 证书到期时间。
- Cron/Timer 任务最近执行结果。
- 安全配置漂移摘要：SSH、防火墙、计划任务、用户账户变化。
- 历史报告归档：提供上一期报告入口和下一期预计生成时间。

### 7.8 硬件健康

- CPU 温度、磁盘温度。
- 风扇转速。
- 电源/UPS 状态（如存在）。
- 硬件错误日志。

### 7.9 安全与入侵研判

报告必须直接回答“本周期是否有异常，是否像入侵”：

- CPU 持续高占用：超过阈值的最长持续时段。
- 内存持续高占用：超过阈值的最长持续时段。
- 磁盘 I/O 异常：周期内峰值繁忙度、出现时间和设备。
- 网络异常：出站流量突增、连接数突增、未知端口外联。
- 可疑程序：未知名称、周期平均高占用、异常启动路径。
- 异常登录：来源、时间、频率和历史习惯差异。
- 新监听端口：周期内是否出现未知端口。
- SSH 授权密钥变化：周期内是否新增或删除授权密钥。
- 计划任务变化：周期内是否新增或修改 Cron/Timer。
- 系统账户变化：周期内是否新增、删除或锁定账户。

展示要求：

- 异常检测只展示结论和关键数据，不展示检测逻辑。
- 无异常项显示“未发现”，避免用户逐项猜测。
- 可疑项必须能引导到具体证据，例如时段、进程、来源 IP。
- 风险摘要与异常研判合并为单张明细表，字段为“研判项、结论、风险等级、说明”；风险计数放在章节引导句，不再单独重复风险汇总表。

### 7.10 建议与行动项

报告最后按严重程度输出行动建议：

```text
[高] 磁盘 /data 使用率已达 88%，按当前增速预计 45 天后写满。
[中] 发现 3 个服务处于失败状态：radarr、sonarr、qbittorrent。
[中] 存在 12 个安全更新未安装。
[低] Docker 容器 jellyfin 在报告周期内重启 8 次。
```

建议必须是可执行的，并尽量给出命令或模块入口，不能只输出原始指标。

行动项状态要求：

- 每条建议必须带状态：`待处理`、`处理中`、`已解决`。
- 状态使用文字和胶囊标签，风险等级使用高/中/低徽章。
- 已解决的问题只保留到本周期报告，不再进入下一周期建议。

### 7.11 优秀报告对标与增强建议

参考 WhaTap 性能报告、NinjaOne 系统健康快照、SRE Four Golden Signals 和批量巡检报告后，建议按以下优先级补充能力：

| 优先级 | 增强项 | 优秀报告做法 | 建议落地方式 |
|--------|--------|-------------|-------------|
| P1 | 周期对比 | 每个关键指标都标注“较上一周期变化”，例如 `+15% WoW` | CPU、内存、流量、登录、更新、磁盘增长全部增加与上一周期对比 |
| P1 | 可用性与 SLA | 报告必须给出周期可用性百分比和计划内/外停机 | 新增可用性区块：`7 天可用性 99.95%`、计划重启 1 次、非计划停机 0 次 |
| P1 | 统一事件/变更时间线 | 将重启、更新、服务重启、配置变化、事件合并为一条时间线 | 新增“本周期事件”表，按时间排序并标注影响 |
| P1 | 资源占用大户 | 巡检报告通常列出 TOP 程序 | 资源章节新增过去一周平均利用率 Top 5 程序 |
| P1 | 数据覆盖度 | 报告明确哪些指标有完整数据、哪些缺失 | 摘要下方显示 `7/7 天资源数据`、`登录日志覆盖 N 天` |
| P1 | 行动项闭环 | 优秀报告会说明问题当前状态和下一步动作 | 行动项增加“待处理/处理中/已解决”状态字段 |
| P1/P2 | 服务稳定性周期指标 | SRE 建议关注延迟、流量、错误、饱和度 | 对关键服务和 Docker 容器统计周期错误次数、重启次数、最近启动时间；可逐步加入 Nginx 错误率 |
| P1/P2 | 磁盘 I/O | 仅看容量不够，应包含读写吞吐和设备繁忙度 | 资源章节补充磁盘 I/O 摘要 |
| P2 | 安全配置漂移 | 优秀安全报告会提示 SSH、防火墙、计划任务是否被修改 | 记录关键配置快照，报告显示是否有变化 |
| P2 | 历史报告归档 | 用户可回溯上一期并对比趋势 | 报告页脚提供上一期报告路径或入口 |

参考来源：

- WhaTap Performance Reporting：https://docs.whatap.io/en/best-practice-guides/scenario-performance-report
- NinjaOne System Health Snapshot：https://www.ninjaone.com/blog/how-msps-can-present-system-health-snapshots/
- Splunk SRE Four Golden Signals：https://www.splunk.com/en_us/blog/learn/sre-metrics-four-golden-signals-of-monitoring.html
- Linux 批量巡检报告：https://github.com/Zhh9126/linuxcheck

## 8. 功能需求

### FR-01 模块入口与菜单

**需求描述：**

`ops-report` 二级菜单只保留用户直接可用的操作，不要求用户理解数据采集、数据覆盖或模块生命周期等内部概念。菜单固定提供四个报告周期和定时报告启用/禁用入口；用户点击生成报告时，系统自动完成依赖安装和数据采集初始化。

**菜单示例：**

```text
运维报告
> 启用定时报告
  禁用定时报告
  生成最近 7 天报告
  生成最近 30 天报告
  生成最近 180 天报告
  生成最近 365 天报告
```

**业务规则：**

1. 菜单固定展示上述 6 个入口，不因 sysstat 数据覆盖天数而隐藏或禁用生成入口。
2. `启用定时报告` 与 `禁用定时报告` 是幂等操作：已启用时再次启用不报错，未启用时再次禁用不报错。
3. `启用定时报告` 自动完成依赖安装、sysstat 与日志保留初始化，并注册固定周报/年报。
4. `禁用定时报告` 仅移除 cron 任务，保留手动生成入口、历史报告和已采集数据。
5. 点击任意生成入口时，先自动检查并安装缺失依赖，再生成对应周期报告；安装失败则终止并提示，不生成不完整报告。
6. 数据不足时不阻止生成，报告必须明确标注实际覆盖范围。
7. 用户仅浏览菜单时不生成报告、不修改状态。
8. 菜单返回行为与项目其他二级菜单保持一致。

### FR-02 生成报告

**需求描述：**

用户选择周期后立即生成对应报告。

**业务规则：**

1. 支持 `7d`、`30d`、`180d`、`365d` 四种周期。
2. 终端输出摘要，本地只生成 HTML 详细报告。
3. 报告文件保存在 `/var/lib/debnas/ops-report/reports/`，只保存 `.html` 文件。
4. 交互模式默认发送邮件，不再询问；未配置通知邮箱时由发送组件自动跳过。CLI 通过 `--email` / `--no-email` 控制。
5. 菜单固定展示全部周期，数据不足时不阻止生成，但报告开头必须提示缺失范围。
6. 报告生成失败时不能标记模块成功。
7. 生成报告前自动初始化运行环境：检查并安装缺失依赖、启用 sysstat 采集与日志保留；该过程幂等。

### FR-03 CLI 入口

**需求描述：**

支持命令行生成报告，便于脚本和定时任务调用。

**命令示例：**

```bash
debnas --yes run ops-report --period 7d
debnas --yes run ops-report --period 1m --email
debnas --yes run ops-report --period 6m
debnas --yes run ops-report --period 1y
```

**业务规则：**

1. 周期参数支持 `7d/1w`、`30d/1m`、`180d/6m`、`365d/1y`。
2. 非法周期回退到 `7d` 并提示。
3. 非交互模式不弹菜单。
4. CLI 生成行为与菜单一致：自动初始化依赖和数据采集，不要求先启用定时报告。

### FR-04 定时报告

**需求描述：**

定时报告采用固定周期，不提供用户修改调度；用户只能启用或禁用定时报告。

**业务规则：**

1. 每周一 01:00 自动生成并发送最近 7 天报告。
2. 每年 1 月 1 日 02:00 自动生成并发送最近 365 天报告。
3. 年度报告同时支持随时手动生成。
4. 定时模式默认发送邮件，由代码常量控制，不提供配置文件。
5. `启用定时报告` 时自动初始化依赖、sysstat 与日志保留，并注册固定 cron 任务。
6. `禁用定时报告` 时移除 cron 任务；保留手动生成入口、历史报告和已采集数据。
7. 定时任务执行前检查数据覆盖；数据不足时跳过本次发送，不生成不完整报告，并在状态文件记录跳过原因。
8. 现有 cron 框架默认单模块单条目，实现时通过日期门控或最小扩展支持周报和年度报告两个固定任务。
9. 模块元数据 `@cron_schedule` 固定为 `0 1 * * 1`，作为周报主调度；年度报告通过日期门控或最小 cron 扩展实现。

### FR-05 数据初始化与保留

**需求描述：**

生成报告或启用定时报告时，自动完成数据采集与保留策略初始化；用户不需要单独执行“启用数据采集”。

**业务规则：**

1. 检测 `sysstat`；未安装时通过现有依赖体系安装。
2. 检测 `smartctl`；缺失时按项目依赖体系安装 `smartmontools`，不依赖未实现的磁盘健康模块。
3. 启用 `/etc/default/sysstat` 的 `ENABLED="true"`。
4. 配置 `/etc/sysstat/sysstat`：
   - `HISTORY=400`
   - `COMPRESSAFTER=14`
   - `SADC_OPTIONS` 包含 `-S DISK -S XDISK`
   - 考虑 `-D` 使用 `saYYYYMMDD` 文件命名，避免历史文件被覆盖。
5. 通过 logrotate 保留 `wtmp`、`btmp`、`wtmpdb` 约 13 个月。
6. 配置修改使用 `write_file_if_changed`，不破坏用户已有配置。
7. 如果系统已有 sysstat 历史，应尽量保留并纳入报告。
8. 初始化动作由生成报告和启用定时报告自动触发，重复执行幂等，不重复安装依赖或清空历史。

### FR-06 数据覆盖提示

**需求描述：**

报告必须诚实展示数据覆盖情况。

**业务规则：**

1. 数据覆盖天数按 sysstat 文件实际覆盖的自然日数计算，不以文件数量代替连续覆盖。
2. 报告标注 sysstat 数据最早日期。
3. 登录数据标注 `wtmp/btmp/wtmpdb` 实际可追溯范围。
4. 如果某板块无数据，显示“无数据/未启用”，而不是显示为 0。
5. 如果报告周期长于实际数据范围，头部元数据行显示黄色警告。

### FR-07 邮件通知

**需求描述：**

报告可发送到已配置的通知邮箱，并将本地生成的 HTML 详细报告作为邮件附件一并发送。

**业务规则：**

1. 复用 `/etc/exim4/notify_email` 和现有邮件发送模式。
2. 邮件正文优先发送 Markdown；如邮件系统不支持 Markdown，则降级为纯文本或 HTML 内容。
3. HTML 详细报告作为标准 MIME 附件发送，附件文件名为 `ops-report-YYYYMMDD-HHMMSS.html`。
4. 邮件正文与 HTML 附件并存：正文用于快速浏览摘要，附件用于查看完整报告，不要求用户二选一。
5. 附件发送通过本地消息组装完成，不依赖 `mutt`、`mailx` 等外部邮件客户端。
6. 附件缺失、超过 `OPS_EMAIL_MAX_ATTACH_BYTES` 或 MIME 组装失败时，自动降级为仅发送正文，并记录警告，不阻断报告生成。
7. 未配置邮件时，提示用户先配置 `mail-account`，不阻塞终端报告。
8. 邮件发送失败不阻断报告生成。
9. 不保存 `.md` 文件，邮件内容在生成时直接构造。
10. HTML 详细报告保存在本地供用户通过浏览器查看。

### FR-08 状态与日志

**需求描述：**

运维报告模块遵循 DebNAS 统一状态和日志机制。

**业务规则：**

1. 生成报告成功后由 `module-runner` 记录模块状态。
2. 报告文件路径、生成耗时、数据覆盖范围写入模块状态。
3. 定时执行失败时进入 `state` 失败记录。

### FR-09 禁用与数据保留

**需求描述：**

用户可禁用定时报告；禁用不删除历史报告和采集数据。

**业务规则：**

1. `禁用定时报告` 仅移除 cron 任务，保留手动生成入口和数据采集。
2. `启用定时报告` 重新注册固定周报/年报，不改变固定周期。
3. 保留 `/var/lib/debnas/ops-report/` 下的报告和历史数据。
4. 不修改 sysstat 的长期保留策略，避免破坏用户其他用途。
5. 重新启用时直接复用已有数据，不重复安装依赖或清空历史。

## 9. 数据源与技术方案

### 9.1 技术选型

| 数据 | 数据源 | 说明 |
|------|--------|------|
| CPU | `sar -u` | sysstat 标准历史数据 |
| 内存 | `sar -r` | 含内存和 Swap |
| 磁盘 I/O | `sar -d` | 需要 `SADC_OPTIONS` 含 `DISK` |
| 文件系统容量 | `sar -F` | 需要 `SADC_OPTIONS` 含 `XDISK` |
| 网络流量 | `sar -n DEV` | 按接口统计收发 |
| 更新历史 | `dpkg.log`、`apt/history.log` | 统计周期内更新次数和包明细 |
| 登录记录 | `last`/`wtmpdb last` | Debian 12 与 Debian 13 分开处理 |
| 失败登录 | `lastb`、`auth.log`、journald | Debian 13 以 auth/journal 为主要来源 |
| 服务状态 | `systemctl --failed` | 与 `service-query` 语义一致 |
| 磁盘健康 | `smartctl`、`/proc/mdstat`、`findmnt`、journald | 由 `ops-report` 内置采集，不依赖磁盘健康模块 |
| Docker | `docker ps`、`docker inspect` | 容器状态和重启次数 |
| 虚拟机 | `virsh`、进程状态 | 仅检测可用能力，不强依赖 |
| 硬件温度 | `sensors`、`smartctl` | 无传感器时自动隐藏 |
| 更新 | `apt`、sys-patches 状态 | 复用现有检查结果 |
| 物理硬盘映射 | `lsblk` | 将挂载点聚合到物理硬盘 |

### 9.2 模块结构

```text
modules/ops-report/
├── module.sh    # 菜单、CLI、cron 分发
├── setup.sh     # 启用/禁用、sysstat 与日志保留配置
├── health.sh    # SMART/RAID/文件系统硬件健康检查
├── report.sh    # 数据聚合，生成含内联图表的 HTML 报告与邮件内容
├── security.sh  # 登录、失败登录、封禁、账户审计
├── services.sh  # systemd、Docker、VM 状态
└── notify.sh    # 可选邮件通知
```

### 9.3 与现有体系集成

- 复用 `feature_enable/disable` 管理功能开关。
- 复用 `cron_register/cron_unregister` 管理定时任务。
- 生成报告与启用定时报告共用同一套依赖检查和数据初始化流程；`cron_is_registered` 仅用于定时状态展示，不改变菜单结构。
- 所有模块参数直接定义为代码常量，不新增模块配置文件。
- 复用 `state_set` 记录报告状态。
- 复用 `check_dependencies` 和依赖分级。
- 复用 `mail-account`/`exim4` 发送邮件。
- 在 `timer-manager.sh` 的 `TIMER_MODULES` 中登记 `ops-report`。
- 在 `lib/system/dependency.sh` 中补充 `sar`、`sadc`、`wtmpdb` 等命令映射。

### 9.4 Debian 12/13 兼容

- Debian 12：使用 `last`/`lastb` 读取 `wtmp`/`btmp`。
- Debian 13：使用 `wtmpdb last` 读取 `wtmp.db`，失败登录从 `auth.log`/journald 读取。
- 模块运行时自动检测系统版本，不硬编码命令。

## 10. 非功能需求

### 10.1 性能

- 报告生成不得影响 NAS 正常服务。
- 7 天报告目标在 10 秒内完成。
- 365 天报告目标在 60 秒内完成，具体以参考硬件验证。
- 大量日志读取使用 `--since`/`--until` 限制范围，不全量扫描。

### 10.2 兼容性

- 支持 Debian 12.x/13.x amd64。
- 支持无 `sensors`、无 Docker、无 VM 的轻量环境，缺失部分自动隐藏。
- `smartctl` 作为模块依赖优先自动安装；仍无法读取时显示“不可用”，不阻塞其他板块。
- HTML 报告可离线打开，不依赖外部网络、CDN 或 JavaScript 运行时。

### 10.3 安全

- 报告文件默认权限 `600`，目录权限 `700`。
- 邮件只发送到已配置的通知邮箱。
- 报告中的登录 IP 和时间属于敏感数据，不得写入普通日志。
- 不采集密码、Token、密钥等敏感内容。

### 10.4 可维护性

- 数据读取、聚合、输出逻辑分离，便于维护 HTML 和未来 PDF。
- 所有命令调用遵守项目安全约束：超时、路径检查、禁止 `eval`。
- 模块全部函数保持纯 Bash 实现。

## 11. 代码常量

本模块不提供配置文件，也不通过 DebNAS 配置体系读取用户参数。所有参数直接在脚本中定义为 `readonly` 常量，修改参数等同于修改代码。

```bash
OPS_DEFAULT_PERIOD=7
OPS_EMAIL_ENABLED=1
OPS_EMAIL_ATTACH_HTML=1
OPS_EMAIL_MAX_ATTACH_BYTES=2097152
OPS_REPORT_DIR="/var/lib/debnas/ops-report"
OPS_SYSSTAT_HISTORY=400
OPS_INCLUDE_DOCKER=1
OPS_INCLUDE_VM=1
OPS_INCLUDE_SMART=1
OPS_INCLUDE_SENSORS=1
```

常量说明：

- `OPS_DEFAULT_PERIOD`：CLI 未指定周期时的默认值，`7/30/180/365`。
- `OPS_EMAIL_ENABLED`：定时报告是否发送邮件，默认开启。
- `OPS_EMAIL_ATTACH_HTML`：是否将 HTML 详细报告作为邮件附件发送，默认开启。
- `OPS_EMAIL_MAX_ATTACH_BYTES`：HTML 附件大小上限，默认 2 MB，超过后降级为仅正文。
- `OPS_REPORT_DIR`：报告文件保存目录。
- `OPS_SYSSTAT_HISTORY`：sysstat 历史保留天数，默认 400。
- `OPS_INCLUDE_*`：是否尝试采集对应板块，缺工具时自动降级。
- 红黄绿评级阈值固定写在脚本常量中，不提供用户配置。

## 12. 验收标准

### AC-01 模块入口

- 菜单中出现「运维报告」模块，归属「系统维护」。
- 进入菜单仅浏览时不生成报告、不记录成功状态。
- 菜单固定展示 6 个入口：启用定时报告、禁用定时报告、生成最近 7/30/180/365 天报告。
- 生成入口不因数据覆盖不足而隐藏或禁用。
- 点击生成报告时自动安装缺失依赖并初始化数据采集。
- 禁用定时报告后手动生成入口仍然存在。

### AC-02 报告周期

- 可通过菜单生成 `7d/30d/180d/365d` 报告。
- 可通过 CLI 使用 `--period 7d|1m|6m|1y` 生成报告。
- 非法周期回退到 `7d` 并提示。

### AC-03 报告内容

- 报告包含本周概览、资源、存储、登录安全、服务状态、维护建议。
- 报告包含本周概览和内联 SVG/CSS 图表。
- 本周概览包含周结论、每日状态时间条和 3 项关注事项；风险数量与风险明细由第 2 章统一呈现。
- 报告第 2 章为“安全与入侵研判”，以单张明细表呈现风险等级和异常研判结论，风险计数位于章节引导句。
- 报告头部包含标题、状态行和本周概览。
- 系统维护包含周期内更新次数、更新包数量和更新明细。
- 登录审计包含 24 小时时段分布和时段异常登录提示。
- 网络部分包含阶段汇总、单位明确的收发流量。
- 网络作为独立章节展示，仅统计物理网卡。
- 磁盘容量按物理硬盘统计，不单列挂载点。
- 资源章节包含磁盘容量使用率与 90% 阈值图，以及按设备比较周期累计读/写量和峰值繁忙度的 I/O 图；磁盘容量与 I/O 合并为一张明细表。
- 登录审计包含来源 IP 统计整宽表：成功/失败次数、带年份的最后登录时间、来源类型、来源合计和 Fail2ban 封禁说明。
- 每项指标包含平均值、峰值和最繁忙时间。
- 数据不足时报告显示覆盖范围。
- 报告包含周期可用性、统一事件时间线、周期平均利用率 Top 5 程序和磁盘 I/O 明细。
- 报告包含服务稳定性周期指标、安全更新待装数量、配置漂移。
- 服务稳定性章节包含错误次数与重启次数对比图，并保留服务稳定性明细表。
- 报告包含系统版本更新表：操作系统、内核和关键组件版本变化。
- 报告包含 Swap、系统负载、重启需求和 Journal 错误摘要。
- 行动项带 `待处理/处理中/已解决` 状态，页脚提供上一期报告归档入口。
- 停机统计区分计划内、非计划、意外停电，报告只展示分类结果和持续时间。
- 报告包含“安全与入侵研判”章节，展示持续高占用、异常流量、可疑进程和异常登录结论。
- 安全与入侵研判覆盖新监听端口、SSH 授权密钥、计划任务和系统账户变化。
- 磁盘 I/O 使用 sysstat 周期采样的平均/峰值/最繁忙时段；当前状态指标必须标注“报告生成时”。

### AC-04 定时报告

- 启用后 `cron_is_registered("ops-report")` 返回真。
- 定时任务固定为每周一 01:00 生成 7 天报告，每年 1 月 1 日 02:00 生成 365 天报告。
- 禁用后 cron 任务被移除，手动生成入口和历史数据保留。
- 重新启用后重新注册固定调度。
- 数据不足时定时任务跳过本次发送，不生成不完整报告。
- 重新启用后历史报告保留，模块参数不依赖配置文件。

### AC-05 邮件

- 已配置邮箱时，邮件正文优先发送 Markdown；不支持时发送邮件支持的格式。
- 邮件包含 Markdown/兼容正文和 HTML 详细报告附件，正文用于摘要，附件用于完整报告。
- 附件缺失、过大或组装失败时降级为仅发送正文，并记录警告。
- HTML 详细报告保存在本地，可通过浏览器打开。
- 未配置邮箱时终端报告仍正常生成。
- 邮件发送失败不导致报告生成失败。

### AC-06 数据保留

- sysstat 配置为至少保留 400 天。
- `wtmp`/`btmp`/`wtmpdb` 保留至少 13 个月。
- 报告目录权限为 root 可读，普通用户不可读。

### AC-07 兼容性

- Debian 12 使用 `last`/`lastb` 可生成登录报告。
- Debian 13 使用 `wtmpdb last` 可生成登录报告。
- 无 Docker、VM、传感器时报告仍可生成，仅隐藏对应板块。

### AC-08 质量门禁

- 新增模块通过 `bash tests/check.sh` 全部门禁。
- 增加单元测试、集成测试和 mock 测试。
- 更新 `CHANGELOG.md`。

## 14. 风险与边界

### 14.1 历史数据不可回填

CPU、内存、磁盘 I/O、网络流量的历史数据只有在首次生成报告或启用定时报告并完成 sysstat 初始化后才会开始积累。首次初始化前没有的数据，报告必须提示用户。

### 14.2 登录日志保留不足

如果系统原有 `wtmp`/`btmp` 已轮转删除，登录历史只能追溯到现有日志范围。模块启用后通过 logrotate 策略保证后续保留。

### 14.3 报告内容可能偏多

为避免用户被大量指标淹没，报告默认只展示摘要和关键指标，深度数据通过“详细模式”查看。

### 14.4 隐私风险

登录 IP、用户名、登录时间属于敏感信息。报告文件、邮件和日志权限必须控制，且不能自动发送到未知地址。

### 14.5 硬件能力差异

不同硬件的传感器、SMART、Docker、VM 能力不同。模块应自动降级，不能因缺少某一能力而让整份报告失败。

## 15. 产品决策记录

以下产品决策已经确认，后续设计和开发必须遵循：

1. 定时报告固定为每周一次，不在启用时由用户选择周期。
2. 年度报告默认自动发送，同时支持手动生成。
3. Docker/VM 板块进入 v1.0。
4. 本地报告只保存 HTML；邮件优先发送 Markdown，不支持时降级为邮件支持的格式。
5. 总体状态采用红黄绿评级，阈值按行业标准固定在脚本中，不允许用户自定义。
6. 二级菜单采用简化入口：固定展示 4 个报告周期入口和定时报告启用/禁用入口，不引入数据采集、数据覆盖或模块生命周期等状态化菜单。
7. 生成报告与依赖、数据采集初始化绑定：用户直接点击生成时自动安装缺失依赖，不要求先启用定时报告。
8. 定时报告只有启用/禁用两个动作；禁用仅移除 cron，保留手动生成入口、历史报告和已采集数据。
9. 数据不足时不阻止生成报告，但报告必须明确标注实际覆盖范围。
10. 邮件通知发送 Markdown/兼容正文，并附带本地 HTML 详细报告附件；附件缺失或组装失败时降级为仅正文。
