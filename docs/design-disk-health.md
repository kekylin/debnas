## 0. 评审修订说明

本文档已根据 2026-08-03 的《磁盘健康监测模块方案评审》完成修订，修订内容包含：

- 补齐 Debian 12/13 的 smartmontools 版本差异与 NVMe 自检能力降级策略。
- 重建设备发现与磁盘身份识别规则，避免分区、RAID 逻辑盘和 NVMe namespace 重复监测。
- 增加状态文件并发保护、原子写入与 schema 版本要求。
- 修正首次基线可能掩盖严重存量风险的问题。
- 修正 ATA Error Log 笼统归类为接口告警的问题，并补充 SMART 187/188 的处理。
- 明确告警等级决策表、事件指纹与时间驱动的降频策略。
- 补齐自检状态机、cron 调度约束、SMART 已禁用处理和 smartctl 退出码语义。
- 修正“只读查询”与自检行为冲突，以及扫描范围、验收标准等内部矛盾。
- 定时调度改为在“启用监测”时询问并注册，调度不再由 `disk-health.conf` 的 `CRON_SCHEDULE` 控制，消除配置与 crontab 双数据源。
- 配置文件收敛为 8 项用户可理解的“自检频率与通知策略”参数；温度阈值、SMART 增量阈值、超时和并发等工程参数移入代码常量。

本次修订不改变已确认的产品决策：菜单仅提供“立即检查/启用监测/禁用监测”，不提供独立定时设置菜单；“启用监测”时询问调度，默认每天 00:00 检查；长短自检频率沿用已确认配置。

## 1. 文档目的

本文档用于定义 `disk-health`（磁盘健康监测）模块的产品需求，作为后续设计、开发、测试与验收的唯一需求依据。

本文档面向以下读者：

- 产品经理：确认产品范围、交互流程与业务规则。
- 开发人员：理解功能边界、判定逻辑、配置项与数据存储要求。
- 测试人员：依据“验收标准”设计测试用例并验证交付结果。

## 2. 需求背景与产品目标

### 2.1 背景

DebNAS 面向家庭与小型办公 NAS 场景，磁盘是数据可靠性最关键的硬件组件。当前项目缺少统一的磁盘健康监测能力，用户无法及时发现磁盘介质故障、磨损、接口异常或温度风险。

### 2.2 产品目标

1. 自动发现系统内可见的物理磁盘，并基于 SMART 数据持续监测健康状态。
2. 在磁盘出现健康风险时，通过邮件及时告警。
3. 告警信息必须准确、克制、可执行，避免固定经验阈值造成误导。
4. 全部能力以 DebNAS 现有菜单、定时任务、邮件、配置与状态体系承载。

### 2.3 成功标准

- 用户启用监测后，可在无人工干预的情况下获得周期性检查结果与异常告警。
- 新增磁盘无需重新配置，即可自动纳入下一轮监测。
- 对同一问题的重复通知按既定策略降频，避免骚扰。
- 对厂商未知属性与接口类错误不做误导性解释。

## 3. 术语定义

| 术语 | 说明 |
|------|------|
| SMART | Self-Monitoring, Analysis and Reporting Technology，磁盘自监测、分析与报告技术 |
| smartctl | smartmontools 提供的 SMART 读取命令行工具 |
| 首次接入基线 | 模块首次对某块磁盘采集时保存的快照；新盘通常接近出厂后状态（可能含出厂测试计数），旧盘仅代表开始监测时的状态，不冒充出厂值 |
| 上次基线 | 上一次检查保存的快照，用于判断较上次的增量变化 |
| 降频通知 | 同一问题持续存在时，按“每日 → 每周 → 每月”逐步降低通知频率 |
| 接口告警 | 仅针对已确认属于接口/线缆/背板层面的错误（如 ATA 错误日志中的 ICRC/ABRT 类记录）的告警，不代表介质损坏；ATA Error Log 本身不是接口错误的充分条件 |
| 厂商阈值 | ATA 设备 smartctl 属性表中的 `VALUE/WORST/THRESH`；`WHEN_FAILED` 是 smartctl 根据当前值与最差值对比阈值生成的显示列，仅适用于 ATA 属性表 |
| 属性检查 | 读取 SMART 属性与健康状态，不触发自检 |
| 短自检 | SMART Short Self-Test，通常数分钟完成 |
| 长自检 | SMART Long Self-Test，可能持续数小时至数十小时 |
| 事件指纹 | 用于唯一标识同一告警问题的键，由磁盘标识、问题类别、指标与变化方向组成 |
| 自检状态机 | 管理自检从启动、进行中、完成、失败、中断到不支持的完整状态转换 |

## 4. 产品范围

### 4.1 纳入范围

- 系统可见且 SMART 可读的 ATA/SATA HDD/SSD、NVMe 物理磁盘。
- 支持 SMART 透传的 SAS/SCSI 磁盘（仅解析通用字段，不解析 ATA 属性表）。
- 磁盘发现、属性采集、基线管理、告警分级、邮件通知、短/长自检与定时执行。

### 4.2 不纳入范围

- 硬件 RAID 控制器逻辑盘：系统看到的 `/dev/sdX` 可能不是物理盘，默认不猜测物理盘信息。
- 无 SMART 透传的 USB/SATA 桥接磁盘：仅提示 SMART 不可用。
- `/dev/vd*`（virtio 虚拟磁盘）与 `/dev/mmcblk*`（eMMC）：通常不提供完整 SMART，检测到不支持时跳过。
- 不提供 RAID 创建、分区、格式化、磁盘写操作或破坏性操作。
- 不依赖 smartd 守护进程，本模块以 DebNAS 自有定时任务驱动。

### 4.3 扫描范围

模块通过 `lsblk` 与 `smartctl --scan-open` 发现设备，不再直接使用 glob 扫描设备路径。

发现规则：

1. 使用 `lsblk -dn -o NAME,TYPE,TRAN,MODEL,SERIAL,WWN` 过滤 `TYPE=disk` 的真实磁盘节点，排除分区、设备映射器与明确不支持的设备类型。
2. NVMe 以物理控制器为监测单元（如 `/dev/nvme0`），避免将 `/dev/nvme0n1`、`/dev/nvme0n2` 等 namespace 重复计为多块磁盘；实际设备参数以 `smartctl --scan-open` 返回结果为准。
3. `/dev/vd*`（virtio 虚拟磁盘）与 `/dev/mmcblk*`（eMMC）不在发现范围内，检测到时不纳入、不提示为故障。
4. 硬件 RAID 控制器逻辑盘不猜测物理盘信息；若 `smartctl` 无法返回可识别的物理盘身份，则标记为“RAID 逻辑卷/不支持”，不进入监测。
5. USB/SATA 桥接设备在发现范围内尝试采集；无 SMART 透传时标记“SMART 不可用”，不阻塞其他磁盘。
6. 每次执行时重新扫描，新增磁盘自动纳入下一轮监测，无需用户重新启用功能。

### 4.4 磁盘标识

- 磁盘身份信息必须同时保存并校验：`/dev/disk/by-id/` 标识、序列号、WWN、设备型号、固件版本与容量。
- 无 by-id 时可回退到设备名，但状态文件仍必须校验序列号/WWN/型号/容量，防止设备名变化或磁盘更换导致基线错乱。
- 磁盘被拔出、重新插入或路径变化后，以身份信息重新关联原基线。
- 磁盘更换或同一标识下身份信息不一致时，不得继承旧基线；旧状态文件保留并标记为“已更换”。
- 状态文件名使用经过清洗的稳定标识，不允许直接使用包含路径分隔符或不可信字符的设备名称。

## 5. 功能需求

### FR-01 模块入口与菜单

**需求描述：**

模块名为 `disk-health`，显示名为“磁盘健康监测”，归属“系统维护”分类。

二级菜单固定提供以下功能：

```
磁盘健康监测

> 立即检查
  启用监测
  禁用监测
```

**业务规则：**

1. 用户进入菜单仅浏览时，不执行磁盘扫描、依赖检查、日志记录或状态变更。
2. 依赖检查延迟到用户选择具体动作后执行。
3. 菜单返回行为与项目其他二级菜单保持一致：`Esc` 返回上级，`Q` 不在此菜单退出脚本。
4. 菜单顺序按使用频率排列：立即检查置顶，启用/禁用构成功能开关组。

**验收标准：**

- AC-01：进入菜单不产生“磁盘健康监测”完成日志，不修改功能状态。
- AC-02：三个菜单项均可正常进入，返回行为符合项目统一规范。

### FR-02 启用监测

**需求描述：**

用户选择“启用监测”后，模块应完成依赖检查、默认配置初始化、状态目录初始化、定时调度询问、首次属性检查、注册定时任务，并将模块功能状态置为已启用。

**业务规则：**

1. 依赖 `smartctl`；缺失时按项目工具依赖策略自动安装 `smartmontools`。
2. 交互模式下，“启用监测”先询问定时调度：首次启用时留空使用默认 `0 0 * * *`；已启用时显示当前调度，留空表示保持不变，输入新表达式表示修改。
3. 非交互模式下不询问，使用已保存调度；无已保存调度时使用默认 `0 0 * * *`。
4. 调度表达式必须通过项目 cron 校验，且必须保证至少每天执行一次（第 3-5 字段均为 `*`）；非法或非每日表达式回退默认 `0 0 * * *` 并输出提示。
5. 启用监测同时开启功能状态，并通过 `cron_register` 幂等注册定时任务。
6. 首次属性检查按“首次接入基线”规则执行；接口类存量异常仅报告，严重存量风险发送一次性“基线高风险”提示，不进入每日告警。
7. 启用成功后输出成功日志，并记录动作状态。
8. 配置文件已存在时，“启用监测”只补齐缺失配置项，不覆盖用户已填写的配置值。
9. 已启用时重新执行“启用监测”，以调度确认/更新为主，不重置首次基线，不重复发送基线高风险提示。

**验收标准：**

- AC-03：启用后 `feature_enabled("disk-health")` 返回真。
- AC-04：启用后生成默认配置文件与项目状态目录下的 `disk-health` 状态目录。
- AC-05：启用后 `cron_is_registered("disk-health")` 返回真，调度为用户确认值，默认 `0 0 * * *`。
- AC-52：重新执行“启用监测”后，已有配置项与基线保持不变，cron 条目按用户确认的表达式幂等替换。
- AC-54：启用后生成的默认配置文件仅包含 8 项用户配置参数，不包含已移入代码的工程参数。

### FR-03 禁用监测

**需求描述：**

用户选择“禁用监测”后，模块应禁用功能状态，并移除该模块已注册的定时任务。

**业务规则：**

1. 禁用功能必须同时移除定时任务，避免功能关闭后仍周期性执行。
2. 已采集的历史状态与基线数据保留，重新启用时继续沿用。
3. 不删除历史状态文件；配置文件保留，用户自定义参数在重新启用时继续生效。
4. 最近一次调度保存在状态中；重新启用时默认沿用，用户仍可修改。

**验收标准：**

- AC-06：禁用后 `feature_enabled("disk-health")` 返回假。
- AC-07：禁用后 `cron_is_registered("disk-health")` 返回假。
- AC-08：重新启用后原状态文件仍存在。
- AC-53：禁用后重新启用，默认沿用上次调度，且用户可修改。

### FR-04 立即检查

**需求描述：**

“立即检查”只执行属性检查，不触发短自检或长自检。

**执行入口：**

- 交互菜单：选择“立即检查”。
- 命令行：`debnas --yes run disk-health`。

**业务规则：**

1. 立即检查必须采集全部可读磁盘的 SMART 属性。
2. 检查结果按告警规则判定，需要通知时按事件指纹与通知状态发送邮件。
3. 立即检查不改变定时任务注册状态。
4. 立即检查不要求功能已启用，可独立执行。
5. 立即检查与 cron 定时检查同时执行时，必须通过全局执行锁互斥，后到任务直接跳过或等待。

**验收标准：**

- AC-09：执行立即检查后，状态文件中 `last_seen` 与 `last_*` 快照更新。
- AC-10：立即检查不会启动任何自检任务。
- AC-40：功能未启用时，立即检查仍可正常执行。

### FR-05 定时任务

**需求描述：**

模块不提供独立的“定时设置”菜单。定时任务由“启用监测”询问并注册，默认每天 `0 0 * * *`；用户可在启用时直接输入自定义表达式，已启用时再次执行“启用监测”可修改调度。

**执行规则：**

1. “启用监测”时询问定时表达式，调用项目 `cron_register` 注册定时任务。
2. 定时表达式必须通过项目统一 cron 校验，且必须保证至少每天执行一次（第 3-5 字段均为 `*`）；非法或非每日表达式回退默认 `0 0 * * *` 并输出提示。
3. 已启用时重新执行“启用监测”，以用户确认的新表达式幂等替换原定时条目。
4. 禁用监测时同时移除定时任务。
5. cron 定时执行时，脚本内部根据日期区分任务类型：
   - 普通日：仅属性检查。
   - 短自检日：属性检查 + 启动短自检。
   - 长自检日：属性检查 + 启动长自检。
   - 短自检日与长自检日重叠时，长自检优先。
6. 短自检默认每月 1 日。
7. 长自检默认每 6 个月执行一次，默认起始月份为 1 月、日期为 1 日。
8. cron 执行环境必须显式设置 PATH 与 HOME，使用绝对路径调用 DebNAS 与 smartctl，避免最小环境差异导致命令找不到。
9. cron 执行入口必须获取执行锁；同一轮已有手动或 cron 检查运行时，本轮跳过并记录原因。
10. 最近一次调度保存到状态中，作为重新启用时的默认值。

**验收标准：**

- AC-11：cron 模式下不进入交互菜单，且使用绝对命令路径。
- AC-12：cron 普通日不会启动短/长自检；手动 CLI 触发自检不受日期限制。
- AC-13：cron 短自检日只启动短自检，长自检日只启动长自检。
- AC-36：启用监测时询问调度并注册；用户留空使用默认 `0 0 * * *`，非交互模式使用已保存调度或默认值。
- AC-37：定时表达式非法或非每日执行时回退默认值并输出提示。
- AC-38：已启用时重新执行启用监测，新表达式幂等替换旧表达式。
- AC-39：禁用监测时移除定时任务。

### FR-06 短自检与长自检

**需求描述：**

模块支持通过独立 CLI 参数手动触发自检：

- `debnas --yes run disk-health short`：短自检。
- `debnas --yes run disk-health long`：长自检。

**业务规则：**

1. 短自检启动后等待结果；等待时长不得超过代码常量 `SHORT_TEST_TIMEOUT`（600 秒），超时后状态必须标记为“进行中/未完成”，不得记为“完成”。
2. 长自检只负责启动并记录开始时间，不阻塞脚本。
3. 同一磁盘同一时间只允许一个自检任务；上一轮未结束时不得重复启动。
4. 自检结果通过 `smartctl -l selftest` 与 `smartctl -c` 读取，结合设备类型分别处理 ATA/SCSI/NVMe 自检日志格式。
5. 自检状态必须区分：无记录、进行中、完成无错误、完成有错误、已中断/已中止、不支持、超时未完成。
6. 首次运行没有自检记录时，不得将“无记录”描述为“自检正常”。
7. 16TB 级别机械盘长自检可能超过 30 小时，报告必须显示“进行中”或剩余状态。
8. 系统重启或断电后，必须重新读取设备自检状态：设备报告“中断/恢复/重新开始”时按实际状态转换，不得将“进行中”无限期保留。
9. 触发自检前必须检查设备能力与当前自检状态；NVMe 短/长自检仅在 smartmontools 7.4+ 且设备支持时提供，Debian 12 默认版本不支持时明确显示“当前版本不支持 NVMe 自检”。
10. 自检启动命令本身不等待完成；短自检由模块轮询自检日志等待结果，长自检的完成判定由后续属性检查轮询自检日志完成，报告允许延迟到下一次 cron 执行。

**验收标准：**

- AC-14：短自检结束后，状态文件中自检状态更新为“完成，无错误”或“完成，发现错误”。
- AC-15：长自检进行中再次触发时不会重复启动。
- AC-16：无自检记录的磁盘显示“无记录”。
- AC-41：短自检超过代码常量 `SHORT_TEST_TIMEOUT`（600 秒）仍未完成时，状态为“进行中/未完成”，不输出完成结论。
- AC-42：Debian 12 且 smartmontools 低于 7.4 时，NVMe 自检显示“不支持”，且不影响属性检查。

### FR-07 数据采集

**需求描述：**

模块按设备类型使用明确的 `smartctl` 命令组采集数据，不依赖单一的 `smartctl -a -d auto`。

推荐命令组：

| 设备类型 | 推荐命令 |
|----------|----------|
| ATA/SATA HDD/SSD | `smartctl -H -i -c -A -l error -l selftest -d auto`，可按设备补充 `-n standby,0` |
| NVMe | `smartctl -H -i -A -l error -d auto`；smartmontools 7.4+ 且设备支持时追加 `-l selftest` |
| SAS/SCSI | `smartctl -H -i -A -l error -l selftest` |

**必采字段：**

| 设备类型 | 字段 |
|----------|------|
| ATA/SATA HDD/SSD | 整体健康状态、温度（190/194 等实际输出字段）、SMART 5、187、188、197、198、199、ATA Error Count、错误日志条目类型、通电时长、自检状态 |
| NVMe | Critical Warning 各 bit、温度、Percentage Used、Available Spare、Media and Data Integrity Errors、通电时长、自检状态（版本支持时） |
| SAS/SCSI | 整体健康状态、温度日志、通用介质错误与自检日志字段，不解析 ATA 属性表 |
| 通用 | 设备型号、序列号、WWN、固件版本、容量、by-id、是否在 smartctl 数据库中、smartctl 版本 |

**业务规则：**

1. `smartctl` 调用必须设置超时保护。
2. 检测到 SMART support is Disabled 时，按代码常量 `SMART_ENABLE_AUTO=true` 默认执行 `smartctl -s on` 后重新采集；执行失败或设备不支持时提示并跳过，不得报致命错误。
3. 对 `Unknown_Attribute` / `Unknown_SSD_Attribute` 只记录原始值，不参与固定阈值判断。
4. 型号不在 smartctl 数据库时，报告中明确提示属性含义不确定，并限制对 5/187/188/197/198/199 的解释范围。
5. `WHEN_FAILED` 仅适用于 ATA 属性表；`FAILING_NOW` 作为当前失效信号，`In_the_past` 作为历史风险提示，二者不得重复计级。
6. `smartctl` 返回码按 bitmask 处理：错误日志有记录、历史属性越界、自检日志有错误均不等于命令失败；不得把非零返回码直接当作采集失败。
7. 单块磁盘采集失败、超时或 SMART 不可用时，仅记录该盘异常，不影响其他磁盘采集。
8. ATA Error Log 必须解析错误条目类型：只有可确认的接口类错误（如 ICRC/ABRT 且无介质错误特征）才归为接口告警；UNC/ECC 等介质错误不得归为接口告警。
9. 采集输出必须进入统一解析层；优先使用 `smartctl --json` 加 `jq` 结构化解析，若坚持纯 Bash 文本解析，必须固定 smartctl 版本并维护真实设备输出夹具测试。

**验收标准：**

- AC-17：SATA 盘可解析健康状态、温度、介质类指标与接口错误计数。
- AC-18：NVMe 盘可解析 Critical Warning 与 Percentage Used。
- AC-19：不支持 SMART 的设备被跳过，且模块整体返回成功。
- AC-43：ATA Error Log 中只有接口类错误触发接口告警；介质类错误不会被降级为接口告警。
- AC-44：SMART 已禁用且无法自动启用时，报告明确提示，不静默跳过。

### FR-08 首次接入基线

**需求描述：**

模块不依赖“出厂值”，采用首次接入基线。

**业务规则：**

1. 首次对某块磁盘采集时，将当前 raw/normalized 快照保存为首次基线。
2. 后续每次检查同时记录：
   - 较上次的增量变化；
   - 较首次基线的累计变化。
3. 新盘首次接入时，首轮基线接近出厂后状态，但可能包含出厂测试产生的通电时长或少量错误计数。
4. 旧盘首次接入时，首轮基线只代表开始监测时的状态，不得冒充出厂值。
5. 报告与邮件中必须明确标识“首次基线”。
6. 新盘首轮基线可能包含出厂测试产生的通电时长或少量错误计数，报告措辞使用“接近出厂后状态”，不使用“等于出厂状态”。
7. 建立或复用基线前必须校验磁盘身份信息；序列号/WWN/型号/容量任一不匹配时，不得沿用旧基线。

**验收标准：**

- AC-20：首次检查后状态文件存在 `first_*` 与 `last_*` 两组快照。
- AC-21：第二次检查可同时展示较首次与较上次的变化。

### FR-09 存量异常处理

**需求描述：**

首次采集时已存在的非零指标视为存量异常。接口类存量不进入每日告警；严重介质类存量发送一次性“基线高风险”提示，避免被首次基线掩盖。

**业务规则：**

1. 已确认的接口类存量异常（如 UDMA_CRC=19 且不再增加）仅写入报告提示并保存基线，不进入每日告警。
2. 以下存量异常必须在首次检查时发送一次“基线高风险”提示，但不进入每日告警：
   - SMART 197/198/187 首次采集时非零；
   - SMART 5 非零且 normalized 接近或低于厂商 THRESH，或型号家族明确建议更换；
   - 已知型号的 SATA SSD 磨损属性已接近厂商阈值。
3. 以下明确失效信号不受首次基线影响，仍立即告警：
   - SMART 整体健康状态 FAILED；
   - ATA `WHEN_FAILED` 为 `FAILING_NOW`；
   - NVMe Critical Warning 严重位置位；
   - 自检完成但发现错误。

**验收标准：**

- AC-22：首轮检测到存量 CRC 错误但不增长时，不发送每日告警邮件。
- AC-23：首轮检测到整体健康状态 FAILED 时，立即发送告警。
- AC-45：首轮检测到 197/198/187 非零时，发送一次“基线高风险”提示，且后续不进入每日告警。

### FR-10 告警等级与判定

**需求描述：**

模块使用四级告警等级：低、中、高危、严重。

| 等级 | 判定条件 | 主题标识 | 正文标识 |
|------|---------|---------|---------|
| 严重 | SMART 整体健康状态 FAILED；ATA `WHEN_FAILED=FAILING_NOW`；NVMe Critical Warning 中可靠性降级/只读/备用电源失败位置位；待处理、离线不可校正或报告不可校正扇区较上次新增；属性含义可确认时 187 从 0 变为非 0；自检完成且确认存在读错误 | `[严重]` | 🔴 |
| 高危 | 重分配扇区较上次新增；属性含义可确认时 SMART 188 较上次新增且属于超时/命令类风险；NVMe Percentage Used 达到代码常量 `NVME_PERCENT_CRIT`（90）；NVMe Critical Warning 中备件不足/温度告警位置位；自检失败或中断但未确认读错误；中等异常数量达到代码常量 `MEDIUM_ESCALATION_COUNT`（2） | `[高危]` | 🟠 |
| 中等 | 温度达到设备类型代码阈值（`HDD_TEMP_CRIT`/`SSD_TEMP_CRIT`/`NVME_TEMP_CRIT`）；NVMe Percentage Used 达到代码常量 `NVME_PERCENT_WARN`（80）；已确认的接口类错误较上次新增；关键指标连续代码常量 `TREND_CONSECUTIVE_CHECKS`（2）次增长 | `[告警]` | 🟡 |
| 低 | 仅温度达到设备类型代码阈值（`HDD_TEMP_WARN`/`SSD_TEMP_WARN`/`NVME_TEMP_WARN`），无介质错误指标 | `[提示]` | 🟢 |

**业务规则：**

1. 优先采用厂商权威信号：整体健康状态、ATA `WHEN_FAILED`、NVMe Critical Warning。`WHEN_FAILED` 仅在 ATA 设备上使用，`FAILING_NOW` 与 `In_the_past` 不得重复计级。
2. 介质类指标使用相对上次的增量判断，不设置固定临界值；187/188 仅在属性含义可由 smartctl 数据库或型号家族确认时参与等级判定。SMART 5/187/188/197/198/199 的增量阈值均为代码常量，默认值为 1。
3. NVMe 损耗使用代码常量参考阈值：`NVME_PERCENT_WARN=80`、`NVME_PERCENT_CRIT=90`。
4. 温度阈值按 HDD/SATA SSD/NVMe 分别使用代码常量，不宣称所有厂商统一标准。
5. 只有已确认的接口类错误（如 ATA 错误日志中的 ICRC/ABRT 类记录）单独归类为接口告警；ATA Error Log 整体计数不作为接口告警依据。
6. 同一轮检查中同一磁盘出现代码常量 `MEDIUM_ESCALATION_COUNT`（2）个及以上中等异常时，提升为高危。
7. “持续增长”定义为同一指标在连续代码常量 `TREND_CONSECUTIVE_CHECKS`（2）次检查中均较上次增加。
8. 同一物理根因导致 5/197/198/187 等介质指标同时变化时，合并为最高等级并只保留一条事件，不重复计数。
9. 等级上升时立即发送新等级告警，并按事件指纹重置对应降频状态。
10. NVMe Critical Warning 按 bit 区分：备件不足与温度告警为高危，可靠性降级、介质只读与备用电源失败为严重；实现以 smartctl 输出与 NVMe 规范为准。

**验收标准：**

- AC-24：介质类指标相对上次增加达到对应 delta 时触发对应等级告警；187 从 0 变非 0 触发严重。
- AC-25：仅 HDD 温度达到代码常量 `HDD_TEMP_WARN`（50）时输出“提示”，不出现高危措辞。
- AC-26：NVMe Percentage Used 达到 90% 时输出“高危”。
- AC-27：仅已确认接口类错误增加时输出“接口告警”，正文明确说明不代表介质损坏。
- AC-46：同一物理根因导致多个介质指标变化时，只产生一条最高等级事件。
- AC-47：中等异常数量达到代码常量 `MEDIUM_ESCALATION_COUNT`（2）时升级为高危。
- AC-48：同一指标连续达到代码常量 `TREND_CONSECUTIVE_CHECKS`（2）次增长时触发中等告警。

### FR-11 通知降频

**需求描述：**

同一问题持续存在时，通知按“每日阶段 3 天 → 每周阶段 3 周 → 每月持续通知”逐级降频。

**业务规则：**

1. “同一问题”由事件指纹唯一标识，事件指纹为：`磁盘标识 + 问题类别 + 指标 + 变化方向`，例如 `sda+介质+197+增长`。
2. 通知状态按事件指纹分别保存，包括 `stage`、`last_notify_at`、`next_notify_at`、`first_seen`、`last_value`；不按“磁盘+告警等级”笼统计数。
3. 时间阶段基于真实时间，不依赖检查次数：
   - 首次发现：立即发送，进入每日阶段。
   - 每日阶段：24 小时内最多 1 次，连续 `NOTIFY_DAILY_DAYS` 天，默认 3 天。
   - 每周阶段：168 小时内最多 1 次，共 `NOTIFY_WEEKLY_COUNT` 次，默认 3 次。
   - 每月阶段：`NOTIFY_MONTHLY=true` 时每 30 天最多 1 次，持续到问题解决。
4. 问题恢复：当事件指纹不再命中时，发送一次“已恢复”通知，并清除该事件状态。
5. 告警等级升级：立即发送新等级通知，并按事件指纹重置为每日阶段。
6. 同一事件指标继续增长：立即发送通知，并按事件指纹重置为每日阶段。
7. 邮件未配置或发送失败：不推进 `next_notify_at`，状态记录“通知未发送”，下一次检查重试。
8. cron 长时间未执行：恢复执行后按 `next_notify_at` 判断是否发送，不补发历史阶段。
9. 磁盘更换后旧通知状态不得继承；按新磁盘身份初始化事件状态。

**验收标准：**

- AC-28：同一事件指纹在同一阶段不会超过阶段频率发送。
- AC-29：等级升级时立即发送，并重置降频计数。
- AC-30：问题恢复后发送一次恢复通知。
- AC-49：邮件发送失败时状态不推进，下一次检查重试。

### FR-12 邮件报告

**需求描述：**

模块支持两类邮件：

1. 告警报告：磁盘出现健康风险时发送，按降频策略执行。
2. 自检报告：短自检或长自检完成后发送，与磁盘健康状态无关，不进入降频流程。

**业务规则：**

1. 邮件接收地址复用 `/etc/exim4/notify_email`。
2. 未配置邮件账户时，跳过邮件发送并输出提示，不影响检查流程；通知状态不推进，报告中记录“通知未发送”。
3. 同一轮检查中多块磁盘异常时，合并为单封摘要邮件；单块磁盘异常时发送独立报告。摘要合并不影响每个事件指纹的独立降频。
4. 邮件正文使用固定结构：结果 → 问题 → 需关注 → 关键指标 → 趋势 → 自检 → 建议。
5. 邮件主题保持纯文本。
6. 邮件正文使用受控 emoji 标识章节与状态，不在每一行堆叠。
7. 高等级告警正文必须说明存在“随时损坏风险”或等价表述；低等级告警不出现高危措辞。
8. 接口告警正文必须说明错误属于已确认的接口/线缆/背板层面，并提示检查连接；未确认类型的 ATA Error Log 不写入接口结论。
9. 不生成图片附件，不依赖 HTML。
10. 自检报告由后续检查轮询自检日志生成，允许延迟到下一次 cron 执行。

**邮件主题示例：**

```text
[DebNAS][严重] 磁盘健康告警：/dev/sda 待处理扇区较上次增加（C5）
[DebNAS][高危] 磁盘健康告警：/dev/sda 重分配扇区较上次增加
[DebNAS][告警] 磁盘接口告警：/dev/sda UDMA_CRC 错误较上次增加
[DebNAS][提示] 磁盘健康告警：/dev/sda 温度 61°C
[DebNAS] 磁盘自检报告：/dev/sda 短自检完成
```

**验收标准：**

- AC-31：邮件正文包含设备、型号、健康状态、问题、关键指标与建议。
- AC-32：同一轮检查中多块磁盘异常时只发送一封摘要邮件，且各事件降频状态独立。
- AC-33：自检报告不受降频策略限制。

### FR-13 状态与日志

**需求描述：**

模块必须记录每次检查结果与每块磁盘的历史基线。

**存储要求：**

- 模块运行日志写入 DebNAS 统一日志体系。
- 每块磁盘的状态文件位于 `/var/lib/debnas/state/disk-health/<disk-id>.state`，权限为 600。
- 状态文件包含 `schema_version`、磁盘身份信息、`first_seen`、`first_*` 首次快照、`last_seen`、`last_*` 最近快照。
- 状态文件同时支持较上次与较首次的变化比较。
- 所有状态写入必须采用临时文件 + 原子替换；单次完整检查必须持有 `flock` 执行锁，避免 cron 与手动检查并发写入。
- 状态文件采用版本号管理；解析失败或版本不兼容时不得覆盖旧状态，必须输出错误并等待迁移。
- 磁盘身份信息不一致时不得复用旧基线，旧状态保留并标记“已更换”。

**验收标准：**

- AC-34：每次检查后 `last_seen` 更新。
- AC-35：首次基线数据在后续检查中保持不变。
- AC-50：状态文件包含 `schema_version`，写入过程为原子替换。
- AC-51：cron 与手动“立即检查”同时触发时，只有一个任务执行检查，另一个记录跳过。

## 6. 配置项

配置文件：`/etc/debnas/conf.d/disk-health.conf`

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `SHORT_TEST_DAY_OF_MONTH` | `1` | 每月哪一天做快速自检 |
| `LONG_TEST_INTERVAL_MONTHS` | `6` | 每隔几个月做一次深度自检 |
| `LONG_TEST_START_MONTH` | `1` | 深度自检从几月开始计算 |
| `LONG_TEST_DAY_OF_MONTH` | `1` | 深度自检在哪一天执行 |
| `NOTIFY_DAILY_DAYS` | `3` | 发现问题后连续每天提醒几天 |
| `NOTIFY_WEEKLY_COUNT` | `3` | 之后每周提醒几次 |
| `NOTIFY_MONTHLY` | `true` | 长期问题是否每月持续提醒 |
| `NOTIFY_RECOVERY` | `true` | 问题恢复后是否通知用户 |

所有配置均可由用户覆盖。配置值非法时回退默认值。

默认模板仅生成上述 8 项；旧配置中已移入代码常量的键在升级后忽略，不报错，也不覆盖用户文件。

> 说明：`disk-health.conf` 只控制自检日期与通知策略等用户可理解的参数，不包含定时调度表达式。实际 cron 条目由项目统一 crontab 管理。

### 6.1 移入代码常量的参数

以下参数不开放给用户配置，统一作为代码常量维护：

| 代码常量 | 默认值 | 说明 |
|----------|--------|------|
| `HDD_TEMP_WARN` / `HDD_TEMP_CRIT` | `50` / `60` | HDD 温度关注/临界阈值 |
| `SSD_TEMP_WARN` / `SSD_TEMP_CRIT` | `60` / `70` | SATA SSD 温度关注/临界阈值 |
| `NVME_TEMP_WARN` / `NVME_TEMP_CRIT` | `60` / `70` | NVMe 温度关注/临界阈值 |
| `NVME_PERCENT_WARN` / `NVME_PERCENT_CRIT` | `80` / `90` | NVMe Percentage Used 关注/临界阈值 |
| `REALLOC_DELTA` | `1` | SMART 5 新增阈值 |
| `PENDING_DELTA` | `1` | SMART 197 新增阈值 |
| `UNCORRECT_DELTA` | `1` | SMART 198 新增阈值 |
| `REPORTED_UNCORRECT_DELTA` | `1` | SMART 187 新增阈值 |
| `TIMEOUT_DELTA` | `1` | SMART 188 新增阈值 |
| `CRC_DELTA` | `1` | 已确认接口类错误新增阈值 |
| `MEDIUM_ESCALATION_COUNT` | `2` | 中等异常升级为高危的数量 |
| `TREND_CONSECUTIVE_CHECKS` | `2` | 连续增长判定次数 |
| `SMART_ENABLE_AUTO` | `true` | 是否自动启用 SMART |
| `SHORT_TEST_TIMEOUT` | `600` | 短自检等待超时时间（秒） |
| `SMARTCTL_TIMEOUT` | `30` | 单盘 smartctl 调用超时时间（秒） |
| `MAX_PARALLEL_SCANS` | `4` | 多盘采集最大并行数 |

**定时调度的管理方式：**

1. 首次“启用监测”时询问定时表达式，留空使用默认 `0 0 * * *`。
2. 已启用时再次执行“启用监测”，显示当前调度；留空保持不变，输入新表达式则幂等替换 crontab 条目。
3. 最近一次调度保存到状态文件，禁用后重新启用默认沿用。
4. 自动化用户可通过 `debnas cron enable disk-health "<新表达式>"` 直接修改，不经过菜单。

**为什么定时调度不放入配置文件：**

cron 条目在注册时会把当时的调度表达式写入 root crontab。cron 每次执行时读取的是 crontab 中的快照，不会重新读取 `disk-health.conf`。若在配置文件中保留调度键，会出现“改了配置但 cron 未生效”的双数据源问题，因此调度由 crontab 与状态文件管理，配置文件只负责运行时参数。

**重新执行是否覆盖已填写配置：**

不会。`disk-health.conf` 已存在时，“启用监测”只补齐缺失配置项，不覆盖已有值；自检日期和通知策略等配置在每次检查时实时读取，修改后无需重新启用即在下一次检查生效。

所有配置项在加载时必须校验类型与取值范围；非法值回退默认值并输出提示。

## 7. 非功能需求

### 7.1 兼容性

- 仅支持 Debian 12/13 与 amd64 架构。
- 仅使用 Bash 5.2+，不引入 Python、Node.js、Go 等额外运行时。
- 依赖 `smartmontools`，通过项目依赖体系自动安装。
- Debian 12 默认 smartmontools 7.3 不支持 NVMe 短/长自检与 NVMe 自检日志；模块必须检测 smartctl 版本与设备能力，不支持时降级为“仅属性检查”，不得报错。
- 若使用 `smartctl --json` 结构化解析，`jq` 作为工具依赖纳入项目依赖体系。

### 7.2 性能

- 属性检查必须轻量，单块磁盘 `smartctl` 调用使用代码常量 `SMARTCTL_TIMEOUT`（30 秒）超时。
- 多盘采集支持受控并行，最大并行数由代码常量 `MAX_PARALLEL_SCANS`（4）控制；同一 USB 桥或同一 HBA 链路可限制为串行。
- 对可能处于待机状态的 ATA 盘使用 `-n standby` 策略，避免每次检查唤醒磁盘。
- 长自检不得阻塞主流程，避免影响 NAS 正常业务。
- 16TB 大盘长自检可能超过 30 小时，必须支持“进行中”状态与防重复启动。

### 7.3 安全

- 不执行用户数据写入、分区、格式化或破坏性命令。
- SMART 属性读取为只读操作；短/长自检属于非破坏性设备自检，会占用设备资源，不属于“只读查询”，文档与界面不得将其描述为只读。
- 默认按代码常量 `SMART_ENABLE_AUTO=true` 执行 `smartctl -s on` 启用 SMART，并记录该状态变更；失败时只提示不强制。
- 设备名来自系统扫描，不直接拼接用户输入。
- 所有 `smartctl` 调用使用超时保护。
- 状态文件、配置文件和执行锁权限限制为 root 可读写，避免普通用户读取或篡改。

### 7.4 可维护性

- 按 DebNAS 目录模块规范组织代码。
- 复用项目现有 `cron.sh`、`feature.sh`、`config.sh`、`tempfile.sh`、日志与邮件体系。
- 新增公共能力优先复用项目库函数，不重复造轮子。

## 8. 阈值设定依据与限制

### 8.1 为什么不用固定临界值

SMART 归一化属性、`THRESH` 与 raw 值的含义由各磁盘厂商自行定义，不存在一套通用的固定临界值。因此 `REALLOC_CRIT=50`、`PENDING_CRIT=10`、`SSD_WEAR_CRIT=95` 这类数值不能被当作标准依据。

### 8.2 介质类指标

Backblaze 长期故障统计主要关注 SMART 5、187、188、197、198，并建议部分 HDD 型号中 SMART 187 从 0 变为非 0 后安排更换。该结论基于特定厂商与型号的长期统计，不是所有 ATA/SSD 的通用标准。

本项目对 5/187/188/197/198 采用“相对上次记录的增量判断”，并且：

- 仅在属性含义可由 smartctl 数据库或型号家族确认时，才将 187/188 纳入对应等级判定。
- 未确认含义时只记录 raw 值，不参与等级判定。
- 197 可能因扇区被重分配而下降，198 可能被清除；增量计算必须支持负变化，并在 197 下降、5 上升时合并为同一物理事件。
- ATA Error Log 的总计数不是接口告警依据，必须解析错误条目类型。

### 8.3 NVMe 损耗

NVMe `Percentage Used` 是控制器对寿命消耗的厂商估算，100% 表示寿命耗尽，但并不等于立即故障，且部分设备可能在 100% 后继续运行。行业实践（如 Canonical hardware-observer）使用 80% 警告、90% 严重，本项目作为代码常量默认沿用，不开放普通用户配置，但不得将 80/90 表述为 NVMe 规范失效阈值。

NVMe 判断还应结合 `Available Spare`、`Critical Warning` 各 bit 与 `Media and Data Integrity Errors`，不能只依赖 Percentage Used。

### 8.4 温度阈值

温度阈值按 HDD、SATA SSD、NVMe 分别提供代码常量：HDD 默认 50/60°C，SATA SSD 与 NVMe 默认 60/70°C。这些均属于运行经验参考值，不同盘型与散热环境差异较大，作为代码默认值，不开放普通用户配置，也不宣称所有厂商统一标准。

温度字段来源不统一：ATA 设备可能使用 190 或 194 属性，SCSI 使用温度日志页，NVMe 使用 SMART/Health 温度字段；解析层必须归一化后再参与判定。

### 8.5 真实设备验证

实测 WD HC550（WDC WUH721816ALE6L4）：

- 整体健康状态 PASSED，介质类指标为 0。
- UDMA_CRC_Error_Count 为 19，ATA Error Log 有 19 条 ICRC/ABRT 记录。
- 该盘实测错误均为 ICRC/ABRT，可归类为接口/线缆层面，必须与介质损坏区分。
- 该结论只代表本盘实测结果，不表示所有 ATA Error Log 都是接口错误；其他磁盘出现 UNC/ECC 等记录时必须按介质错误处理。

实测致钛 ZHITAI SC001：

- 不在 smartctl 数据库中，输出大量 `Unknown_Attribute` / `Unknown_SSD_Attribute`。
- 其 raw 值无法按通用百分比解读，固定磨损阈值既可能误报也可能漏报。

实测 16TB WD HC550 长自检建议耗时为 1881 分钟（约 31 小时）。

### 8.6 版本与能力兼容

- Debian 12（bookworm）默认 `smartmontools` 7.3-1，Debian 13（trixie）默认 7.4-3。
- smartmontools 7.4 才新增 NVMe `-t short`、`-t long`、`-l selftest` 支持，且仍标注 experimental。
- 模块必须检测 `smartctl -V` 与设备自检能力，不能假设 Debian 12 与 Debian 13 行为一致。
- ATA `smartctl -a` 在新版 smartmontools 中不再推荐用于完整采集，模块使用按设备类型拆分的命令组。

## 9. 验收总则

1. 所有功能需求必须满足对应 AC 验收标准。
2. 新增或修改代码后必须通过项目质量门禁。
3. 必须在真实磁盘环境执行冒烟测试，至少覆盖 SATA HDD、SATA SSD、NVMe，条件允许时覆盖 SAS/SCSI。
4. 不支持 SMART 的设备必须优雅跳过，不影响其他磁盘监测。
5. 必须分别在 Debian 12 与 Debian 13 上验证属性检查；Debian 12 上额外验证 NVMe 自检能力降级行为。
6. 必须验证以下边界场景：SMART 已禁用、待机盘不唤醒、cron 与手动检查并发、长自检重启中断、短自检超时、邮件发送失败、磁盘更换后不继承旧基线、RAID 逻辑盘跳过、USB 无 SMART 透传跳过。
7. 文本解析实现必须维护真实 `smartctl` 输出夹具，并覆盖 ATA/SCSI/NVMe 三类输出格式。
8. 本需求评审修订完成后，如无新的需求变更，直接作为开发、测试与交付依据。

## 10. 待确认项

无阻塞性待确认项。

编码前需在真实设备上验证并回填结论的项：

- NVMe Critical Warning 各 bit 在目标设备上的实际输出与严重程度映射。
- HDD/SATA SSD/NVMe 温度默认值在真实盘型上的误报率。
- smartmontools 7.4 的 NVMe 短/长自检在目标 NVMe 设备上的可用性。
- `smartctl --json` 在不同设备类型上的字段完整性，以最终确定解析层采用 JSON 还是文本解析。
